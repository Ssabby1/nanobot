# Fitness Agent 面试讲解笔记

这个文档是给你自己面试时准备讲解用的，不面向面试官阅读，不建议放进 README 叙事里。

## 1 分钟版本

我基于开源轻量级 Agent 框架 `nanobot`，做了一个垂直健身场景的 Fitness Agent。它不是开放式聊天机器人，而是把自然语言请求收敛成结构化执行链路，支持用户画像、周计划、日常打卡、调整建议这几个核心闭环。

工程上我主要做了三件事：第一是规则优先、LLM 兜底的路由设计；第二是多轮缺参补全和状态续填；第三是把业务执行统一收口到确定性的 service 层，并补了 deterministic evaluation，保证这个 Agent 不只是能演示，还能回归验证。

## 3 分钟版本

### 项目定位

这个项目是我在 `nanobot` 基础上做的一个垂直 Agent 子项目，目标不是“聊天聊得像人”，而是“在特定场景下能稳定完成任务”。我选的是训练和饮食管理场景，因为它天然适合做结构化输入、状态延续和建议闭环。

### 我做的核心设计

#### 1. 规则优先，LLM 兜底

我没有直接把所有请求都交给大模型自由发挥，而是先做本地规则路由。对于表达很明确的请求，比如建档、生成计划、打卡，这样可以更快、更稳定、成本也更低。只有在表达更模糊或者规则没有命中的时候，才进入 LLM 路由。

但即使是 LLM 路由，我也没有让它直接执行业务，而是要求它输出结构化结果，比如：

- `action`
- `arguments`
- `missing_fields`
- `needs_followup`

最后所有执行还是走同一个 `FitnessService`。这样做的好处是，把“理解”交给路由层，把“执行”收口到服务层，降低模型不确定性。

#### 2. 多轮补全和状态续填

真实用户很少一次把信息说全，所以我做了 pending state。比如用户第一次只说了年龄、身高，系统不会失败，而是记录当前未完成动作，并优先追问最关键的字段。下一轮用户只补缺的部分就能继续。

这里我还处理了两个体验问题：

- 最近活跃用户自动复用，不需要每句话都重新报名字
- 第二轮、第三轮追问文案会随着上下文变化，不像重新开始

这让整个体验更像连续任务，而不是一问一答的命令行脚本。

#### 3. 业务闭环和评测

我不是只做了一个 prompt demo，而是补了完整业务对象和持久化：

- `UserProfile`
- `WeeklyPlan`
- `DailyFeedback`
- `AdjustmentSuggestion`

并且基于这些对象做了计划生成、反馈记录、建议生成这些闭环动作。数据用 `SQLite` 持久化，适合本地快速演示。

另外，我还加了 `nanobot fitness eval`，把常见链路做成 deterministic cases，比如自然语言建档、多轮补全、最近用户复用、打卡后生成建议等。这样项目就不是“我现场点几下能跑”，而是有可回归验证能力。

## 面试官可能追问什么

### 为什么不用纯 LLM Agent？

可以回答：

纯 LLM Agent 在开放场景下很灵活，但在垂直任务里容易把理解和执行混在一起，导致结果不稳定。我这个项目更希望展示工程上的可控性，所以把路由和执行拆开了。规则负责确定性高的部分，LLM 负责语义覆盖不足的部分，service 层负责真正执行。

### 这个项目最难的点是什么？

可以回答：

最难的其实不是生成计划，而是多轮补全和状态延续。因为真实用户输入往往不完整，如果不能自然地续填，这个 Agent 很快就会变成“每一步都要重新说一遍”的假智能体。

### 如果继续迭代会做什么？

可以回答：

我会继续补两个方向：一是把 README、架构图、英文摘要这些对外材料再打磨一下；二是把 eval 做得更完整，例如加入更多边界场景和失败 case，让它更接近一个真正可维护的垂直 Agent 项目。

## 最值得强调的 5 个点

- 把开放式聊天问题收敛成垂直场景下的结构化执行
- 规则优先 + LLM 兜底，而不是纯 prompt 驱动
- 多轮缺参补全和会话状态续填
- 统一 service 执行层，降低模型不确定性
- deterministic evaluation，而不是只靠手工演示

## 不建议对外说得太满的点

- 不要说整个 `nanobot` 框架都是你从零实现的
- 不要把现在的版本说成“生产级产品”
- 不要虚构效果指标、用户规模、性能数据
- 可以明确说这是基于开源框架做的垂直 Agent 工程化改造
