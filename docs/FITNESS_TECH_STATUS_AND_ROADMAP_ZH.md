# 基于 nanobot 的健身 Agent 开发现状与技术路线说明

## 1. 文档目的

本文档用于系统说明我们当前基于 `nanobot` 已经开发完成的内容、正在运行的技术栈、现阶段系统的能力边界，以及下一阶段将继续采用的技术栈、方法和落地路径。

这份文档不是概念性方案，而是面向实际开发交接、继续迭代和后续简历/项目说明的技术文档。文中会明确区分：

- 哪些能力已经在当前代码中实现
- 哪些能力还没有实现，但已经有清晰的下一步方案
- 后续规则路由与 LLM 路由分别会如何接入

---

## 2. 项目背景与当前定位

当前项目是一个基于 `nanobot` 二次开发的健身训练与饮食协同 Agent MVP。

更准确地说，它目前还处于：

- 业务内核已经完成
- 命令行交互链路已经打通
- 数据结构和持久化已经完成
- 一部分中文自然语言归一化已经完成
- 规则建议能力已经初步落地

但它还没有完全升级为一个“用户随便说一句自然语言，系统就能自动识别意图、调用功能、返回结果”的完整对话式 Agent 产品。

因此，当前阶段的定位应该是：

**一个已经具备核心业务能力、可演示、可测试、可继续扩展的 Fitness CLI MVP。**

从演进路径看，它会分成三个阶段：

1. 当前阶段：CLI 业务 MVP
2. 下一阶段：规则路由驱动的自然语言入口
3. 最终阶段：规则路由 + LLM 路由的完整 Agent 化交互

---

## 3. 我们目前已经开发了什么

### 3.1 已完成的业务闭环

目前已经做完并且代码中已经存在的能力包括：

- 用户健身画像建档
- 用户画像的局部更新
- 用户画像查询
- 周训练计划生成
- 周训练计划查询
- 每日训练反馈打卡
- 训练反馈历史查询
- 基于反馈的规则化调整建议生成
- 调整建议查询

这意味着系统已经具备一个完整的最小闭环：

1. 先保存用户画像
2. 根据画像生成训练计划
3. 用户按天打卡反馈
4. 系统基于反馈生成调整建议

这个闭环已经覆盖了一个最基础的“健身训练协同助手”的核心工作流。

### 3.2 已完成的核心数据模型

当前已经实现了完整的结构化数据模型，主要包括四类核心实体：

#### 1. 用户画像 `UserProfile`

已支持字段包括：

- `user_id`
- `gender`
- `age`
- `height`
- `weight`
- `goal`
- `experience_level`
- `training_days_per_week`
- `session_duration`
- `environment`
- `diet_constraint`
- `current_split`
- `weak_points`
- `injury_notes`
- `created_at`
- `updated_at`

这些字段足以支持训练计划生成、饮食建议生成以及后续动态调整。

#### 2. 周计划 `WeeklyPlan`

已支持：

- 计划 ID
- 用户 ID
- 周起始日期
- 目标类型
- 计划版本
- 生成原因
- 每日计划内容
- 生成时间

其中每日计划内容内部还拆成了 `PlanDay` 和 `ExercisePlan` 两层结构，因此计划不仅是文本，而是结构化可扩展数据。

#### 3. 每日反馈 `DailyFeedback`

已支持：

- 是否训练
- 完成动作列表
- 完成度
- 疲劳等级
- 酸痛说明
- 饮食达标情况
- 额外备注
- 日期和创建时间

这为后续做规则分析、趋势分析、自动提醒、训练负荷跟踪奠定了数据基础。

#### 4. 调整建议 `AdjustmentSuggestion`

已支持：

- 建议 ID
- 用户 ID
- 反馈覆盖区间
- 调整类型
- 建议正文
- 触发原因
- 生成时间

这意味着当前“调整建议”并不是简单一句文本，而是有明确来源、触发逻辑和时间上下文的结构化产物。

### 3.3 已完成的输入归一化能力

当前系统已经实现了一部分对自然语言输入很关键的“归一化层”。这部分虽然还不是完整自然语言路由，但已经是 Agent 化的重要基础。

已支持归一化的内容包括：

#### 1. 目标 `goal` 归一化

例如可以把这些说法归一到标准值：

- “减脂和增肌”
- “边减脂边增肌”
- “recomp”
- “新手”
- “入门”

归一后的标准目标包括：

- `瘦肌增肌`
- `减脂保肌`
- `新手入门`
- `增肌`
- `减脂`
- `维持`

#### 2. 训练经验 `experience_level` 归一化

例如：

- “零基础”
- “刚开始健身”
- “系统健身三个月”
- “练了一年”

会被归一到：

- `新手`
- `初级`
- `中级`

#### 3. 训练环境 `environment` 归一化

例如：

- “学校”
- “学校健身房”
- “校园”
- “在家”
- “寝室”

会被映射到：

- `校园健身房`
- `家里`
- `宿舍`
- `商业健身房`

#### 4. 饮食限制 `diet_constraint` 归一化

例如：

- “学校食堂”
- “外卖”
- “自己做饭”
- “自己下厨”
- “有忌口”

会被归一到：

- `食堂为主`
- `外卖为主`
- `自己做饭`
- `忌口`
- `无`

#### 5. 数值归一化

当前已经支持把带单位或范围的输入自动转成标准数值，例如：

- `22岁` -> `22`
- `173cm` -> `173`
- `67kg` -> `67`
- `4-5` -> `5`
- `60-90` -> `90`
- `80%` -> `0.8`
- `80` -> `0.8`

这一步很重要，因为它让系统已经具备“半自然语言参数接收能力”，而不是只能接收纯净、死板的结构化参数。

#### 6. 主观反馈归一化

例如疲劳和饮食状态也已支持部分自然表达：

- “有点累” -> `4`
- “很累” -> `5`
- “还行” -> `基本达标`

这部分是后续规则路由和 LLM 路由的重要基础，因为后续无论从 CLI 自然语言还是聊天对话接入，都需要复用这一层规范化逻辑。

### 3.4 已完成的计划生成逻辑

周训练计划生成已经不是简单模板拼接，而是具备一定规则化生成能力。当前逻辑主要会综合这些维度：

- 训练目标
- 训练经验
- 每周训练天数
- 单次训练时长
- 训练环境
- 薄弱部位
- 伤病限制

当前计划生成能力包括：

- 自动计算一周训练日与休息日分布
- 根据目标和经验选择训练 focus 序列
- 根据训练环境决定动作库
- 根据训练时长决定动作数量
- 根据目标决定组数、次数和训练提示
- 为训练日和休息日分别生成饮食提示
- 在备注中纳入伤病限制和薄弱部位补强建议

当前的训练结构已经包含了下面这些概念层：

- 新手适应
- 全身代谢
- 上肢
- 下肢
- 下肢核心
- 推
- 拉
- 腿
- 上肢推拉
- 上肢补强
- 拉腿补强
- 全身泵感
- 恢复训练

动作库也已经根据“健身房/宿舍/家里”做了不同替换。例如：

- 在器械条件较好时使用卧推、坐姿划船、高位下拉等
- 在家庭/宿舍场景下替换为俯卧撑、弹力带划船、徒手深蹲等

这说明当前生成逻辑已经从“写一段建议文案”进化到“基于画像规则生成结构化训练计划”。

### 3.5 已完成的规则化动态调整建议

当前已经落地了第一版规则驱动的调整建议引擎。已实现的规则包括：

- 连续两次高疲劳，触发降量建议
- 最近反馈中出现明显酸痛，触发动作替换或恢复建议
- 多次未完成计划或缺席训练，触发简化训练建议
- 连续两次饮食未达标，触发现实可执行的饮食替代建议
- 连续多天未训练，触发低门槛重启建议
- 若没有明显风险信号，则给出维持当前计划的建议

当前建议输出不是单一标签，而是多触发因子的组合结果。也就是说，一次生成可能同时包含：

- `deload`
- `exercise_swap`
- `simplify`
- `diet`
- `restart`
- `maintain`

并且系统会同时输出：

- 触发原因
- 建议类型
- 建议正文
- 对应反馈时间范围

这为后续将规则层和 LLM 层组合起来打下了非常好的基础。规则层负责可控性，LLM 层负责自然表达和复杂理解。

### 3.6 已完成的 CLI 入口

当前已经打通了中英文双语 CLI 入口，主要命令包括：

- `nanobot 健身 查看打卡`

- `nanobot 健身 查看建议`

英文入口：

- `nanobot fitness profile-set`
- `nanobot fitness profile-update`
- `nanobot fitness profile-show`
- `nanobot fitness plan-generate`
- `nanobot fitness plan-show`

这说明当前业务能力已经通过 CLI 真正暴露给用户，而不只是内部 Python 函数。

### 3.7 已完成的数据持久化

当前采用 `SQLite` 作为 MVP 阶段的本地持久化方案，数据文件位置为：

- `workspace/fitness/fitness.db`

目前已建立的表包括：

- `user_profiles`
- `weekly_plans`
- `daily_feedback`
- `adjustment_suggestions`

当前实现特点包括：

- 用户画像采用 upsert 方式保存

- 持久化层与 CLI、服务层分离

这种设计对当前阶段非常合适，原因是：

- 部署简单
- 依赖轻
- 本地演示方便
- 查询成本低
- 与 nanobot “轻量级”定位一致

### 3.8 已完成的测试基础

当前仓库里已经有至少两类和本模块直接相关的测试：

- `tests/fitness/test_service.py`

其中已覆盖的重点方向包括：

这说明当前项目并不是“只有演示代码”，而是具备初步可验证性的工程实现。

## 4. 我们目前使用了什么技术栈

### 4.1 基础开发语言与运行环境

当前主开发语言是：

- `Python 3.11+`

这是当前 `nanobot` 项目本身在 `pyproject.toml` 中明确要求的版本范围。

Python 作为当前阶段的主语言非常合适，原因包括：

- nanobot 本体就是 Python 项目
- CLI、数据模型、规则逻辑、持久化都能快速实现
- Pydantic、Typer、SQLite 在 Python 生态里协同非常顺手
- 后续接 LLM provider、Agent loop、工具调用也天然一致

### 4.2 当前主要框架与库

#### 1. `Typer`

用于 CLI 命令定义与参数解析。

在本项目里主要承担：

- 定义命令入口
- 管理中英双语命令别名
- 参数校验
- CLI 输出与异常退出控制

为什么选它：

- 写法比原生 `argparse` 清晰
- 非常适合多命令子系统
- 与类型注解配合自然
- 后续扩展自然语言入口时，仍然可以保留结构化命令作为底层能力

#### 2. `Pydantic v2`

用于定义和校验所有核心业务模型。

在本项目里主要承担：

- 用户画像模型定义
- 周计划模型定义
- 打卡反馈模型定义
- 调整建议模型定义
- 字段类型约束
- 输入归一化前置处理

为什么选它：

- 数据结构清晰
- 校验能力强
- 很适合做“半结构化自然语言输入归一化”
- 后续接 LLM 路由时，也能继续作为函数调用参数校验层

#### 3. `SQLite`

用于 MVP 阶段数据持久化。

在本项目里主要承担：

- 画像存储
- 计划存储
- 反馈存储
- 调整建议存储

为什么选它：

- 零运维
- 单文件部署
- 与 CLI 工具场景天然契合
- 非常适合个人助手、单机演示和快速 MVP

#### 4. Python 标准库 `sqlite3`

当前持久化层没有上 SQLAlchemy，而是直接使用标准库 `sqlite3`。

这是一个很务实的选择，因为当前：

- 表结构简单
- 查询模式固定
- 业务规模小
- 不需要引入额外 ORM 复杂度

#### 5. `nanobot` 自身 Agent 基础设施

当前项目不是从零写一个新 Agent 框架，而是复用了 nanobot 的现成能力，包括：

- CLI 主入口体系
- 配置系统
- workspace 体系
- provider 抽象
- session 管理
- agent loop
- tool 注册体系
- 多渠道接入能力

这也是整个项目最重要的基础设施来源。

### 4.3 当前继承自 nanobot 的上层能力

虽然当前 Fitness MVP 主要先落在 CLI 层，但它天然站在 nanobot 的能力底座之上，因此已经具备未来可接入的上层基础设施：

- 多模型 provider 体系
- LiteLLM 路由能力
- OpenAI / Azure OpenAI / custom provider 支持
- MCP 工具接入能力
- shell / filesystem / web 等工具能力
- session 和 memory 结构
- 多渠道接入能力，例如 Telegram、Discord、Feishu、Slack、QQ、微信等
- Docker / gateway / cron / heartbeat 等运行基础设施

这意味着我们现在做的不是一个孤立脚本，而是在一个真实 Agent 框架上增量开发一个新垂类模块。

### 4.4 当前工程组织方式

当前代码在工程中的主要位置包括：

- `nanobot/fitness/models.py`
- `nanobot/fitness/storage.py`
- `nanobot/fitness/service.py`
- `nanobot/fitness/__init__.py`
- `nanobot/cli/commands.py`
- `tests/fitness/test_service.py`
- `tests/cli/test_fitness_cli.py`

这种组织方式已经体现出清晰分层：

- `models.py` 负责数据建模与输入规范化
- `storage.py` 负责数据持久化
- `service.py` 负责业务编排与规则逻辑
- `commands.py` 负责 CLI 入口适配
- `tests/*` 负责验证

这套结构为下一步接入规则路由和 LLM 路由提供了很好的可扩展性，因为我们不需要推翻已有模块，只需要增加新的“入口层”和“路由层”。

## 5. 当前系统的实际工作方式

为了后续理解下一步方案，先把当前系统的真实工作方式描述清楚。

### 5.1 当前是“显式命令驱动”

用户现在必须明确调用某条命令，例如：

- 建档
- 更新画像
- 生成计划
- 打卡
- 生成建议

系统不会自己理解一句自由表达，例如：

- “我想减脂，帮我建个档”
- “我今天练了胸和背，有点累”
- “给我看看这周训练怎么安排”

也就是说，当前还不是“自由对话式 Agent”。

### 5.2 当前是“业务函数已就绪，路由层还没补”

目前已经有的其实是：

- 稳定的数据模型
- 稳定的持久化层
- 稳定的业务服务层
- 稳定的 CLI 明确入口

真正还没做完的核心，不是业务内核，而是：

- 自然语言意图识别
- 自然语言参数抽取
- 自动选择调用哪个服务函数
- 自动生成更拟人的结果表达

换句话说：

**内核已经有了，现在差的是“把用户自然语言映射到内核能力”的那一层。**

## 6. 当前系统还没有完成什么

当前尚未完成的重点包括：

- 自然语言对话式路由层
- 规则路由模块
- LLM 路由模块
- 统一的 Fitness Agent 对话入口
- Web 页面或 Web Demo
- 更系统化的自动化测试矩阵
- 更精细的训练动作知识库
- 更精细的饮食估算与膳食结构分析
- 更完整的多轮上下文理解

这也是为什么下一步的优先级是先做规则路由，最后再补 LLM 路由。

## 7. 下一步我们将会用什么技术栈

这一部分只写“将要采用且与当前架构兼容”的技术路线，不写空泛设想。

### 7.1 总体原则

后续技术栈延续当前路线，不会推翻已有实现。核心原则是：

- 继续以 Python 为主语言
- 继续复用 nanobot 的 Agent 基础设施
- 继续保留 Pydantic 作为参数约束和归一化层
- 继续保留 SQLite 作为 MVP 阶段数据库
- 先做规则路由，再补 LLM 路由
- 路由层新增，不重写业务层

也就是说，未来新增的主要是：

- 路由模块
- 自然语言解析模块
- Agent 入口适配层
- 更完整的测试用例

而不是重做：

- 画像模型
- 计划生成核心
- 调整建议逻辑
- 持久化结构

### 7.2 下一步仍会继续使用的技术栈

后续会继续使用：

- `Python 3.11+`
- `Typer`
- `Pydantic v2`
- `SQLite`
- `nanobot` 的 provider / agent / session / tools 基础设施

原因很直接：

- 当前代码已经形成稳定层次
- 业务复杂度还没大到需要数据库迁移
- 规则路由完全可以在现有 Python 代码里快速实现
- LLM 路由也天然和 nanobot provider 体系兼容

### 7.3 后续在 LLM 路由阶段会使用的技术基础

当进入 LLM 路由阶段时，我们将主要复用 nanobot 已有的模型能力与 provider 抽象，包括：

- `LiteLLM` 兼容的 provider 路由
- `OpenAI` 类模型
- `Azure OpenAI`
- `custom provider`
- nanobot 的模型配置与默认 agent model 机制

到那一步，LLM 的职责不会是“直接生成所有业务逻辑”，而是主要负责：

- 理解自然语言意图
- 抽取参数
- 在规则不能稳妥覆盖时辅助决策
- 对结构化结果进行自然语言润色与解释

换句话说：

**规则层负责确定性，LLM 层负责弹性理解和自然表达。**

---

## 8. 下一步我们将采用什么方法推进

### 8.1 先做规则路由，不先做 LLM 路由

这是一个非常重要的技术决策。

我们不会一上来就让 LLM 接管所有用户输入，而是先做规则路由。原因包括：

- 当前业务范围比较明确，适合先用规则覆盖
- 规则路由可控性更高，便于调试
- 规则路由更容易写测试
- 规则路由没有模型成本
- 规则路由能更快把 CLI MVP 升级成“更像 Agent 的产品”
- 后续即使接入 LLM，规则层也仍然有价值，不会浪费

### 8.2 规则路由阶段的目标

规则路由阶段要解决的问题是：

用户不再需要输入固定命令，而是可以输入自然中文短句，系统自动判断应该做什么。

例如未来希望支持：

- “我想建个健身档案”
- “我 22 岁，173，67kg，平时在学校练，帮我建档”
- “给我生成一下这周计划”
- “我今天练了卧推和划船，完成度 80%，有点累”
- “最近老是很累，帮我看看怎么调”

这时系统需要做的事情是：

1. 识别意图
2. 判断对应到哪个业务动作
3. 提取参数
4. 如果参数不足，提示用户补充
5. 调用现有 service 层
6. 返回格式化结果

### 8.3 规则路由阶段的技术方法

规则路由阶段我们计划采用：

- 关键词匹配
- 动词/短语模式识别
- 参数正则提取
- 归一化函数复用
- 缺参校验
- 显式 action 映射表

更具体地说，规则路由模块会把自由输入先转换成统一动作，例如：

- `save_profile`
- `update_profile`
- `show_profile`
- `generate_weekly_plan`
- `show_weekly_plan`
- `record_feedback`
- `show_feedback`
- `generate_adjustment`
- `show_adjustment`

然后再从文本中解析参数。

例如：

- “帮我建档，我 22 岁，173cm，67kg，在学校健身房练”
  - action -> `save_profile`
  - args -> `age=22, height=173, weight=67, environment=校园健身房`

- “我今天练了卧推和划船，80%，有点累，饮食还行”
  - action -> `record_feedback`
  - args -> `completed_exercises=[卧推, 划船], completion_rate=0.8, fatigue_level=4, diet_adherence=基本达标`

### 8.4 规则路由阶段的模块设计

建议新增的代码组织会是：

- `nanobot/fitness/router.py`
- `nanobot/fitness/parser.py`
- `nanobot/fitness/actions.py`

职责划分建议如下：

#### `router.py`

负责：

- 识别用户意图
- 决定调用哪个 action
- 管理 fallback 策略

#### `parser.py`

负责：

- 从自然语言中提取参数
- 调用已有归一化逻辑
- 输出结构化参数字典

#### `actions.py`

负责：

- 将 action 名映射到 service 层具体方法
- 统一错误处理
- 统一结果格式化

这种设计的好处是：

- 路由与业务逻辑解耦
- 后续接 LLM 时可以共用 action 层
- 规则匹配和参数提取可以分别演进
- 更容易写单元测试

### 8.5 规则路由阶段的输出方式

规则路由阶段不需要一开始就进 agent loop，也可以先提供一层新的 CLI 入口，例如：

- `nanobot fitness chat --message "..."`
- 或直接在现有 agent/CLI 对话入口里挂一个 fitness 专用分发器

推荐的演进顺序是：

1. 先做一个简单的文本入口，验证自然语言到 action 的映射
2. 再把它接到 nanobot 的对话入口中

这样做的好处是我们可以先验证路由正确率，再考虑对话体验。

---

## 9. 最后我们将如何完善 LLM 路由

LLM 路由不会替代规则路由，而是作为更高层的兜底与增强层。

### 9.1 为什么最后再补 LLM 路由

因为如果一开始就只靠 LLM：

- 结果不够稳定
- 调试成本高
- 不容易写 deterministic 测试
- 参数抽取容易飘
- 容易把简单问题复杂化

但当规则路由打底之后，LLM 的价值会非常明显：

- 处理更自由、更模糊的表达
- 处理多意图混合输入
- 生成更自然的解释文本
- 在规则无法识别时兜底

### 9.2 LLM 路由阶段的职责

LLM 层主要承担四类工作：

#### 1. 意图识别兜底

当规则无法可靠判断输入属于哪个 action 时，交给 LLM 做分类。

例如：

- “我最近练得很乱，帮我整理一下接下来怎么练”

这种表达不够标准，但 LLM 通常能理解其更接近“生成建议”或“生成计划”。

#### 2. 复杂参数抽取

当一段输入里混入很多自然描述时，LLM 可以帮助抽取结构化字段，例如：

- “我在学校健身房训练，平时一周 4 到 5 次，每次大概一个多小时，想边减脂边保肌”

LLM 可以把这段话提取为结构化参数，再交给 Pydantic 校验与归一化。

#### 3. 多轮补全

如果缺少关键参数，LLM 可以帮助生成更自然的追问话术，例如：

- “已经知道你的训练环境和目标了，还差年龄、身高和体重，我再补齐这些就能帮你建档。”

#### 4. 结果润色

当前 service 层已经能输出结构化结果，但未来可以让 LLM 把结果转成更自然、更贴近教练风格的表达，例如：

- 用更自然的中文解释为什么建议降量
- 用更容易执行的方式解释饮食替代
- 根据用户上下文生成更有人味的反馈

### 9.3 LLM 路由阶段的建议实现方式

建议实现成“分层式路由”：

1. 规则先跑
2. 规则命中且置信度足够高，直接执行
3. 规则未命中或参数冲突，再调用 LLM
4. LLM 输出结构化 action + args
5. 再经过 Pydantic 和业务校验
6. 最终调用 service 层

即：

**用户输入 -> 规则路由 -> LLM 兜底 -> 参数校验 -> 业务执行 -> 文本输出**

这条链路比“用户输入后直接让模型自由发挥”安全得多，也更符合工程化要求。

### 9.4 LLM 路由阶段推荐的提示词方法

后续做 LLM 路由时，建议采用“结构化输出提示”而不是开放式问答提示。

推荐让模型输出类似这种结构：

```json
{
  "action": "record_feedback",
  "arguments": {
    "trained_today": true,
    "completed_exercises": ["卧推", "划船"],
    "completion_rate": 0.8,
    "fatigue_level": 4,
    "diet_adherence": "基本达标"
  }
}
```

这样做的好处是：

- 更容易程序接收
- 更容易做 schema 校验
- 更容易 fallback
- 更容易记录错误样本
- 更容易持续优化 prompt

### 9.5 LLM 路由的安全与边界

即使未来上了 LLM，也建议坚持以下原则：

- 不让模型直接写数据库
- 不让模型自由决定未定义 action
- 所有参数都先过 Pydantic 校验
- 所有业务动作都必须经过显式 action 映射
- 模型只负责“理解”和“表达”，不直接承担最终执行权

这会极大降低路由误判和业务漂移风险。

## 10. 后续阶段建议的测试方法

为了让规则路由和 LLM 路由可持续迭代，后续测试建议分三层做。

### 10.1 单元测试

主要覆盖：

- 文本到 action 的映射
- 参数提取
- 参数归一化
- 缺参识别
- service 层行为不回归

例如：

- 输入“帮我建档，我 22 岁，173cm”
  - 应识别为 `save_profile`
  - 应提取 `age=22`, `height=173`

### 10.2 集成测试

主要覆盖：

- 输入一句自然语言
- 路由层识别 action
- 调用 service
- 返回最终结果

这会验证整条链路是否打通。

### 10.3 案例集回归测试

建议额外维护一批中文真实表达样本，覆盖：

- 建档类表达
- 打卡类表达
- 调整建议类表达
- 模糊表达
- 错误表达

后续每次修改规则或 prompt，都跑这套案例集，避免“修一个、坏一片”。

---

## 11. 为什么这条技术路线是合理的

当前这条路线的核心优势在于：

- 没有推翻已有代码
- 先把确定性能力做实
- 再引入模型增强体验
- 与 nanobot 原有能力天然兼容
- 能持续演进成真正的对话式 Agent

简单说，这不是从零起一个新项目，而是：

**先在 nanobot 上做出一个垂直业务 MVP，再把它逐步升级为可自然对话、可路由、可扩展的健身 Agent。**

---

## 12. 建议的开发顺序

建议后续按下面顺序推进：

1. 先补规则路由
2. 为规则路由补单元测试和案例集
3. 打通一个自然语言入口
4. 将自然语言入口接入 nanobot Agent 对话链路
5. 再补 LLM 路由兜底
6. 再补结果润色和多轮追问
7. 最后再考虑 Web Demo 或前端展示

这个顺序的优点是：

- 每一步都可验证
- 每一步都能演示
- 每一步都不会大改底层
- 每一步都能复用上一步成果

## 13. 一句话总结

当前我们基于 `nanobot` 已经完成了一个具备真实业务闭环的健身 Agent CLI MVP，已经落地了画像建档、计划生成、每日打卡、规则化调整建议、输入归一化、SQLite 持久化和中英双语命令入口。

接下来的技术路线会继续沿用 `Python + Typer + Pydantic + SQLite + nanobot Agent 基础设施` 这条轻量工程路线，先补规则路由，把显式命令升级成自然语言可调用的业务系统；最后再补 LLM 路由，让系统在保持可控性的前提下获得更强的意图理解、参数抽取和自然表达能力。
