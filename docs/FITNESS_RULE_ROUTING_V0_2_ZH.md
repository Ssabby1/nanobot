# 基于 nanobot 的健身 Agent 规则路由版本说明

## 1. 文档目的

本文档用于说明当前基于 `nanobot` 开发的健身 Agent 在“规则路由版本”阶段已经完成了什么、使用了什么技术栈、核心实现方法是什么，以及这一版本相对于前一个 CLI 基础版的升级点。

这份文档对应的是：

- 基础业务 MVP 已完成
- 规则路由已完成
- LLM 路由尚未接入

因此它适合作为当前阶段的开发交接文档、阶段总结文档和后续继续接入 LLM 路由前的技术基线说明。

---

## 2. 当前版本定位

当前版本可以定义为：

**Fitness Agent Rule Routing v0.2 阶段版本。**

和上一个基础版相比，这一版的核心变化不是业务能力新增，而是交互方式升级。

上一版的特点是：

- 业务函数已经齐全
- 主要通过显式 CLI 命令调用
- 仍然偏“命令式工具”

这一版的特点是：

- 已经支持规则驱动的自然语言路由
- 已经能识别用户意图并自动调用业务动作
- 已经支持在 `agent -m "..."` 场景下直接短路到健身规则系统
- 已经具备“更像真实 Agent”的自然语言交互入口

所以这次升级的本质是：

**把 Fitness CLI MVP 升级成了一个规则驱动的自然语言健身 Agent 原型。**

---

## 3. 当前已经完成的能力

### 3.1 业务能力仍然完整保留

当前规则路由版本完全复用了基础版已完成的业务内核，仍然具备以下完整能力：

- 用户画像建档
- 用户画像更新
- 用户画像查询
- 周训练计划生成
- 周训练计划查询
- 每日训练反馈打卡
- 打卡历史查询
- 动态调整建议生成
- 调整建议查询

也就是说，规则路由不是另外写一套业务逻辑，而是把自然语言入口映射到已有业务服务层。

### 3.2 已完成的规则路由能力

当前规则路由层已经支持以下意图识别：

- `save_profile`
- `update_profile`
- `show_profile`
- `generate_weekly_plan`
- `show_weekly_plan`
- `record_feedback`
- `show_feedback`
- `generate_adjustment`
- `show_adjustment`

这意味着当前规则路由层已经把健身业务闭环的主要动作全部覆盖完整。

### 3.3 已完成的自然语言入口

当前已经支持两种自然语言入口方式。

#### 1. Fitness 专用路由入口

```powershell
nanobot fitness route "我叫sasa，我是男，23岁，176cm，70kg，目标是增肌，初级，每周4次，每次60分钟，在家训练，外卖为主"
```

这条入口会直接进入健身规则路由器，进行意图识别、参数抽取、业务执行和结果输出。

#### 2. Agent 入口短路模式

```powershell
nanobot agent -m "给我生成这周训练计划"
```

如果输入内容明显属于健身业务意图，系统会优先尝试走健身规则路由，而不是立刻交给通用 LLM Agent。

这个设计让系统开始具备：

- 更自然的交互
- 更低的模型依赖
- 更快的本地响应
- 更稳定的业务执行

### 3.4 已完成的用户标识自然提取

当前规则路由版本已经支持从自然语言中提取用户标识，而不再强依赖 `--user-id demo`。

例如支持：

- “我叫 sasa”
- “我的名字是 sasa”
- “叫我 sasa”

系统会自动把提取出的名字作为 `user_id` 使用。

因此现在已经支持这种用法：

```text
我叫 sasa，我是男，23岁，176cm，70kg，目标是增肌，初级，每周4次，每次60分钟，在家训练，外卖为主
```

用户不再需要先手动写一遍：

- `--user-id sasa`

这一点是当前规则路由版本的重要升级点。

### 3.5 已完成的活跃用户记忆

当前新增了一层轻量级路由状态保存，会在 `workspace/fitness/router_state.json` 中记录最近一次活跃用户。

这意味着系统现在不仅能从一句话里识别出用户，还能在后续没有再次显式说名字时继续沿用最近一次活跃的健身用户。

例如：

第一句：

```text
我叫 sasa，我是男，23岁，176cm，70kg，目标是增肌……
```

第二句：

```text
给我看看我的画像
```

第三句：

```text
给我生成这周训练计划
```

系统已经可以顺着同一个用户继续执行，而不需要每一句都带 `sasa`。

### 3.6 已完成的缺参提示

当前规则路由不会在信息明显不足时盲目执行，而是会主动提示用户缺少哪些关键信息。

例如输入：

```text
帮我建档，我是男，23岁
```

系统会识别出这是建档意图，但会提示还缺少：

- 身高
- 体重
- 目标
- 训练经验
- 每周训练天数
- 单次训练时长
- 训练环境
- 饮食条件

这种行为非常重要，因为它保证了：

- 路由结果可解释
- 系统行为可控
- 不会凭空编造结构化参数

## 4. 当前版本技术栈

### 4.1 语言与运行环境

当前版本仍然基于：

- `Python 3.11+`

该版本依旧延续 nanobot 的 Python 主体架构，不引入新的后端语言。

### 4.2 核心工程技术栈

当前规则路由版本使用的技术栈包括：

- `Python`
- `Typer`
- `Pydantic v2`
- `SQLite`
- `sqlite3`
- `nanobot` Agent 基础设施

具体职责如下。

#### 1. `Typer`

负责：

- CLI 命令注册
- `fitness route` 命令入口
- `agent -m` 单消息入口
- 参数解析和错误退出

#### 2. `Pydantic v2`

负责：

- 用户画像模型校验
- 周计划模型校验
- 打卡反馈模型校验
- 调整建议模型校验
- 输入归一化

#### 3. `SQLite + sqlite3`

负责：

- 用户画像持久化
- 周计划持久化
- 打卡反馈持久化
- 调整建议持久化

#### 4. `nanobot` 现有基础设施

继续复用：

- CLI 主命令系统
- 配置加载系统
- workspace 路径体系
- Agent 命令入口
- provider 抽象
- session / memory / tools 体系

这也是为什么当前规则路由版本可以自然接进 `nanobot agent -m`，而不用重做整套交互链路。

## 6. 详细实现方法

这一部分是当前版本最重要的技术说明。

### 6.1 规则路由总体思路

当前规则路由遵循的是：

**自然语言输入 -> 规则识别 -> 提取结构化参数 -> 调用业务服务 -> 输出格式化结果**

它不是直接让模型自由发挥，而是由一套确定性的规则驱动。

### 6.2 意图识别方法

当前意图识别主要采用：

- 关键词匹配
- 场景短语匹配
- 规则优先级判断

例如：

- “建档 / 建个档 / 创建档案” -> `save_profile`
- “更新画像 / 修改档案” -> `update_profile`
- “查看画像 / 我的档案” -> `show_profile`
- “生成计划 / 这周怎么练” -> `generate_weekly_plan`
- “查看计划 / 看看计划” -> `show_weekly_plan`
- “打卡 / 我今天练了” -> `record_feedback`
- “查看打卡 / 打卡记录” -> `show_feedback`
- “给我建议 / 怎么调” -> `generate_adjustment`
- “查看建议 / 最近的建议” -> `show_adjustment`

这种识别方式的优点是：

- 快
- 稳
- 可测试
- 可解释

### 6.3 参数提取方法

参数提取主要采用正则和固定词表。

#### 1. 用户画像参数提取

会提取：

- 性别
- 年龄
- 身高
- 体重
- 目标
- 训练经验
- 每周训练次数
- 单次训练时长
- 训练环境
- 饮食条件
- 薄弱部位
- 伤病限制
- 当前分化

提取方式包括：

- 正则提数字和单位
- 固定词表识别目标/经验/环境/饮食条件
- 归一化层做最终标准化

#### 2. 计划参数提取

目前主要提取：

- 周日期

例如支持：

- 明确日期 `2026-03-27`
- “这周”
- “本周”
- “下周”

#### 3. 打卡参数提取

目前主要提取：

- 日期
- 是否训练
- 动作列表
- 完成度
- 疲劳程度
- 饮食达标情况
- 酸痛说明
- 补充说明

例如：

```text
我今天练了卧推和划船，完成度80%，有点累，饮食还行
```

会提取出：

- `trained_today = True`
- `completed_exercises = ["卧推", "划船"]`
- `completion_rate = 0.8`
- `fatigue_level = 4`
- `diet_adherence = 基本达标`

### 6.4 用户标识解析方法

规则路由版本新增了用户标识解析方法。

当前优先级如下：

1. 如果显式传了 `--user-id`
2. 如果文本里有“我叫 xxx / 我的名字是 xxx / 叫我 xxx”
3. 如果有已保存的最近活跃用户
4. 如果数据库里只有一个 profile，则默认使用它
5. 最后回落到 `default`

这套顺序的好处是：

- 明确参数优先级最高
- 用户自然表述可以覆盖大多数单人场景
- 同一 workspace 下的连续使用体验更流畅

### 6.5 最近活跃用户记忆方法

当前实现使用：

- `workspace/fitness/router_state.json`

保存字段：

- `last_user_id`

当规则路由成功执行一次健身动作后，会自动把当前用户写入这个状态文件。之后如果用户继续说：

- “给我看看我的画像”
- “这周怎么练”
- “看看最近的建议”

系统会优先沿用最近一次的健身用户，而不需要再次声明名字。

### 6.6 路由执行方法

规则命中后，并不会在路由层内部重复写业务逻辑，而是统一调用 `FitnessService`。

映射关系如下：

- `save_profile` -> `service.save_profile`
- `update_profile` -> `service.update_profile`
- `show_profile` -> `service.get_profile`
- `generate_weekly_plan` -> `service.generate_weekly_plan`
- `show_weekly_plan` -> `service.get_latest_plan`
- `record_feedback` -> `service.record_feedback`
- `show_feedback` -> `service.list_feedback`
- `generate_adjustment` -> `service.generate_adjustment`
- `show_adjustment` -> `service.get_latest_adjustment`

这样做的核心好处是：

- 路由层只做路由
- 业务层只做业务
- 代码职责清晰
- 后续 LLM 路由可以复用同一套 action 执行层

### 6.7 `agent -m` 短路接入方法

为了让用户不必总是写：

- `nanobot fitness route "..."`

当前在 `nanobot agent -m "..."` 单消息入口里加入了一层健身优先短路逻辑。

逻辑顺序是：

1. 先检查输入是否能命中 Fitness 规则路由
2. 如果命中，直接在本地执行 Fitness 路由
3. 如果未命中，再继续走原来的通用 Agent / LLM 流程

这个设计的意义非常大，因为它让当前系统已经开始支持更自然的使用方式：

```powershell
nanobot agent -m "我叫sasa，我是男，23岁，176cm，70kg，目标是增肌……"
```

而且对于明显的健身请求，不依赖模型、不依赖 API key，也能直接工作。

## 8. 当前规则路由版本的边界

虽然这一版已经可以视为“规则路由完成版”，但它仍然是规则系统，不是最终完整智能路由系统。

当前边界包括：

- 仍然主要依赖显式规则，不处理特别模糊的复杂表达
- 多意图混合输入仍然不够强
- 还没有引入 LLM 做复杂语义兜底
- 用户追问和复杂多轮补全还比较基础
- 健身知识覆盖仍然偏 MVP 级别

所以这一版适合定义为：

**规则路由完成版，但不是最终智能路由终版。**

---

## 9. 下一步建议

在规则路由完成后，下一步最合理的方向就是开始准备 LLM 路由层。

建议顺序如下：

1. 保留当前规则路由作为第一层
2. 引入 LLM 做模糊表达兜底
3. 引入结构化 action + arguments 输出
4. 继续复用当前 service 层执行
5. 用 LLM 做结果润色和多轮补全

也就是说，未来架构会变成：

**规则路由优先，LLM 路由兜底。**

---

## 10. 一句话总结

当前我们已经把基于 `nanobot` 的健身 Agent 从“CLI 基础版”推进到了“规则路由完成版”。

这一版不仅保留了画像、计划、打卡、建议这一整套完整业务能力，还新增了自然语言意图识别、自动参数提取、自动用户标识识别、最近活跃用户记忆，以及 `agent -m` 场景下的健身短路分流能力。

从工程角度看，这一版已经是一个真正可用、可演示、可继续演进到 LLM 路由阶段的规则驱动健身 Agent 原型。
